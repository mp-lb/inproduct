---
title: Managed file library
description: Verified uploads to versioned S3, quotas, retention holds and durable audit, with metadata in your own MongoDB.
---

The managed file library in `@mp-lb/inproduct-storage` hides object keys, version pins,
upload capabilities, verification, quotas and retention holds behind file UUIDs. Bytes
stay in a versioned S3 bucket. Metadata lives in a MongoDB database your application
owns. Your application keeps identity, authorization decisions, domain records,
configuration and UI.

It is a different API from the [small-file storage](/docs/storage) `createFileStorage`,
which stores bytes inside its adapter. Use the file library when files are large,
must be verified before use, or are referenced by other records.

## Installation

The file library ships in `@mp-lb/inproduct-storage` from the release that first
contains the `/file-library` entry points. Check availability with
`npm view @mp-lb/inproduct-storage exports` before depending on it. It requires Node.js
22.13+ and ESM.

```sh
pnpm add @mp-lb/inproduct-storage mongodb @aws-sdk/client-s3 @aws-sdk/s3-request-presigner
```

MongoDB and the AWS SDK are optional peer dependencies: install them only when you use
the Mongo or S3 adapters. Each entry point has one job:

| Entry point | Runtime | Contents |
| --- | --- | --- |
| `/file-library` | Browser or Node | Zod schemas, `FileView`, `FileExplorerClient`, `formatFileValidationError` |
| `/file-types` | Browser or Node | [File type registry, identification, names and download policy](/docs/file-types) |
| `/file-library/server` | Node | `createFileLibrary`, contracts, `FileStorageError`, `createFileReferenceCoordinator`, `createFileAuditDispatcher`, `createFileByteValidator`, `createClamdScanner`, `scanPrivateFileBytes` |
| `/file-library/testing` | Node | Memory repository and reference store, synthetic object driver and scanner |
| `/s3` | Node | `createS3FileDriver`, `createPrivateFileStore`, `createVersionedDocumentStorage` |
| `/node` | Node | `createMongoFileLibraryRepository`, `createMongoFileAuditLedger`, `createMongoFileReferenceStore` |

Never wire `/file-library/testing` into a production composition. Its scanner is a
fixture, not malware protection.

## Initialize

```ts
import { createFileLibrary } from '@mp-lb/inproduct-storage/file-library/server';
import { createClamdScanner } from '@mp-lb/inproduct-storage/file-library/server';
import { createS3FileDriver } from '@mp-lb/inproduct-storage/s3';
import { createMongoFileLibraryRepository } from '@mp-lb/inproduct-storage/node';

const s3 = createS3FileDriver({
  bucket: config.bucket, // versioning must be enabled
  region: config.region,
  prefix: 'app/file-library/',
});

const library = createFileLibrary({
  repository: createMongoFileLibraryRepository(db, 'files'),
  driver: s3.driver,
  scanner: createClamdScanner({ endpoint: config.clamdUrl, readVersion: s3.readVersion }),
  quotaBytes: 1024 ** 3,
  authorize: async ({ actor, action, file, scope, consumer }) =>
    yourPolicy.allows(actor, action, { file, scope, consumer }),
});
```

`config`, `db` and `yourPolicy` are your application's. Every method takes a trusted
`actor` (`{ id, tenantId }`) that your server resolves from its session, never from
request JSON.

## Consumer integration

A host typically exposes the library through its own authorized API:

1. **Begin.** Validate the request with `beginFileSchema` and call
   `library.begin(actor, input)`. Send the uploaded file name as `name` and, optionally,
   the browser's `File.type` as `contentType`. The library resolves the canonical type. You
   do not map extensions or MIME types yourself. It reserves quota and returns a stable file
   UUID and a short-lived upload ticket. Retrying with the same `operationId` and identical
   input returns the same file; changed input conflicts.
2. **Upload.** The browser PUTs the bytes to `ticket.upload.url` with
   `ticket.upload.headers`. Use the ticket's `Content-Type`, which is the resolved type, not
   `File.type`. The S3 signature binds type, length, SHA-256 and a
   conditional create.
3. **Finalize.** `library.finalize(actor, fileId)` pins one immutable version, checks
   size, type and checksum, validates bytes and scans. Retries rescan the pinned version
   and can never repin it. Scanner or provider failures leave the file retryable.
4. **Link.** Associate the available file with a domain record using `library.link`.
   Use retention holds separately only when your application needs to block deletion.
5. **Audit.** A trusted worker drains each tenant's audit outbox with
   `createFileAuditDispatcher(repository, ledger)`.

The package test `consumerIntegrationExample.test.ts` runs this flow end to end with
the synthetic adapters.

## File types and names

Each file has an editable `name` and one library-managed type. `FileView` carries:

| Field | Meaning |
| --- | --- |
| `name` | The editable name without its extension, such as `Q3 report.v2`. |
| `extension` | The extension compatible with the type, such as `pdf`. Renames never change it. |
| `fileName` | The safe download name, `name` plus `extension`. Show it wherever the full name is expected. |
| `contentType` | The canonical media type. It equals `type.id`. |
| `type` | `{ id, label, status }`, such as `{ id: 'application/pdf', label: 'PDF document', status: 'recognized' }`. |

Renaming with `edit` changes only `name`. A trailing extension the file already has is removed,
so sending `Q3.pdf` for a PDF stores `Q3`. Any other suffix stays in the name: `Q3.html`
downloads as `Q3.html.pdf`. The bytes, version, type and extension never change.

### Type policy

`createFileLibrary({ fileTypes })` sets which types uploads may have and the evidence each one
needs. By default all types, including unknown types, are accepted. The library uses an exact
content check where available, otherwise a compatible family check, otherwise no format check.
Unchecked content remains inferred or unknown and is downloaded as a generic attachment.
Checksums, version pinning and any configured malware scanner still apply.

```ts
import { createFileTypeRegistry } from '@mp-lb/inproduct-storage/file-types';
import { createFileByteValidator } from '@mp-lb/inproduct-storage/file-library/server';

const registry = createFileTypeRegistry({
  types: [{ id: 'application/vnd.acme.board+json', label: 'Acme board', extensions: ['acmeboard'] }],
});

const library = createFileLibrary({
  // …repository, driver, scanner, quota, authorize
  byteValidator: createFileByteValidator(s3.readVersion, registry),
  fileTypes: {
    registry,
    accept: ['application/pdf', 'text/csv', 'application/vnd.openxmlformats-officedocument.wordprocessingml.document', 'application/vnd.acme.board+json'],
    contentCheck: 'compatible',
    contentChecks: { 'application/pdf': 'exact' },
    onConflict: 'reject',
  },
});
```

| Option | Default | Behavior |
| --- | --- | --- |
| `registry` | built-in | The registry used for resolution, labels and names. Pass the same registry to `createFileByteValidator` and `createClamdScanner`. |
| `accept` | all types | Optional type ids or aliases. With a list, other types fail with `INVALID_INPUT` before quota is reserved. Include `application/octet-stream` to allow unknown types. |
| `contentCheck` | automatic; `exact` with an allowlist | `exact` needs a positive byte identification. `compatible` also accepts a matching container or text family. Automatic uses the strongest check supported for each type, or `unchecked` if none is available. |
| `contentChecks` | none | Per-type overrides. `unchecked` accepts a type without content matching. Size, checksum, version pinning and malware scanning still apply. |
| `onConflict` | `reject` | What happens when the file name and the reported type disagree: `reject`, `prefer-extension` or `prefer-declared`. |

The policy is validated at construction. `createFileLibrary` throws if an accepted type is
unknown, or if the built-in detector cannot enforce its check, for example legacy `.doc` under
`exact`. Choose `compatible`, or opt in with `unchecked` and enforce the format in your own
`byteValidator`.

**Begin infers, finalize checks.** `begin` resolves the type from the name and reported type
only, so new files start as `inferred`. `finalize` passes the type and its `contentCheck` to the
byte validator and scanner. Bytes that do not satisfy the check quarantine the file. When a
`byteValidator` runs, the status becomes `recognized` or `compatible`. A validator can return
`{ valid, typeStatus }` to report exactly what it saw, and a plain `true` implies the status of
the check. Without a byte validator the status stays `inferred`, even when the ClamAV scanner
also checks bytes, because the library cannot see the scanner's evidence. Configure
`createFileByteValidator` when you want recognized types shown and served.

A broad registry does not weaken any other guarantee. Authorization, tenant isolation, quota,
checksums, immutable version pins, malware policy and holds are unchanged, and type evidence
is never a safety verdict.

### Downloads

`library.download` signs the pinned version with `fileName` and a served type chosen by
[`describeFileDownload`](/docs/file-types#download-responses). The response is always an
attachment. The canonical type is served only for `recognized`, non-active types; everything
else is served as `application/octet-stream`. Custom `ObjectDriver`s receive `name` and
`contentType` and must respond as an attachment.

### Records from 0.1.6 and earlier

Earlier records stored the full uploaded file name in `name` and have no `extension` or
`typeStatus`. They need no backfill. On read, the library splits the stored name against the
stored type with the same rules as new uploads:

- `report.v2.pdf` as PDF becomes `report.v2` + `pdf`.
- `scan.jpeg.pdf` as PDF becomes `scan.jpeg` + `pdf`.
- `notes` as plain text becomes `notes` + `txt`, and downloads as `notes.txt`.
- A name that does not match its type keeps its full name: `report.pdf` stored as plain text
  downloads as `report.pdf.txt`.
- A type the registry does not know keeps the full name with no extension, and its label
  comes from the media type.

Legacy files report `inferred` status and download as `application/octet-stream`. The first
`edit` writes the record in the new shape. `fileRecordName(record, registry)` in
`/file-library/server` gives the same split, if you want to backfill or migrate references.

## Extension contracts

The library calls these host-supplied functions. Each boundary stays in your application.

| Contract | Responsibility |
| --- | --- |
| `authorize(input)` | The authorization decision. Return false unless the exact request is allowed. Actions are `upload`, `read`, `write`, `download`, `attach`, `release`, `delete`, `diagnostics` and `configure`. `scope` is a request, not a grant. Verify consumer identities such as `project:P-1`. |
| `FileRepository` | An atomic, durably acknowledged revision compare-and-swap per tenant partition. |
| `ObjectDriver` | Upload signing, version inspection and download signing. Must declare `versioned`, `checksum` and `conditionalCreate`; the library refuses to run otherwise. |
| `Scanner` / `ByteValidator` | Inspect the exact pinned version and detect content rather than trusting the upload MIME type. |
| `FileReferenceStore` | The authoritative association between a domain record and a file. |
| `FileAuditLedger` | An idempotent append, keyed by tenant and event ID. |

Storage independently enforces tenant isolation, lifecycle, version immutability and
hold restrictions. List results are authorized row by row before filtering and
pagination, so cursors never reveal hidden rows.

## MongoDB configuration

`createMongoFileLibraryRepository(db, collectionName = 'files')` stores one document per
file in the collection you choose. Revision, quota and the pending audit outbox live in
`<collectionName>Settings`. Every change runs in a snapshot transaction with majority and
journal acknowledgment.

**A MongoDB replica set is required.** A single-node replica set works for local
development, for example `mongodb/mongodb-atlas-local`. Standalone servers are not
supported, and there is no non-transactional mode.

`createMongoFileAuditLedger(db, collectionName = 'fileStorageAudit')` and
`createMongoFileReferenceStore(db, collectionName = 'fileStorageReferences')` are
single-document adapters. Pass a `Db` scoped to your application's database and restrict
database access to the server.

## Record links

The library owns associations in a separate collection. Initialize the repository with
`createMongoFileLibraryRepository(db, 'files', 'fileLinks')`; the third argument defaults
to `<collectionName>Links`. Existing files need no migration and initially have no links.
File metadata, links and audit events commit in the same transaction.

```ts
await library.link(actor, { fileId, type: 'matter', targetId: matterId });
const page = await library.list(actor, { linkedTo: { type: 'matter', targetId: matterId } });
await library.unlink(actor, { fileId, type: 'matter', targetId: matterId });
```

List results include `links`, containing each target's `type` and `targetId`. This is the
source of truth; do not also persist an array of file IDs on the target record. Repeating
a completed link or unlink is safe. Concurrent changes can return `CONFLICT`; reload and
retry. Linking requires an available file; unlinking also works after soft deletion.
Soft deletion preserves links for administration and audit history.

Links are many-to-many by default. Configure `maxLinksPerType: { matter: 1 }` in the
library options to allow at most one matter per file. The limit is enforced inside the
atomic mutation, including concurrent requests. Unlink before linking to another matter.

The host's authorization callback receives `link` for the `link` and `unlink` actions.
Verify target existence and permissions there. Read permission is also required. A link
does not grant access, transfer ownership or create a retention hold. Your application
chooses what these associations mean and how target deletion is handled. Target labels
and navigation URLs belong to the application's UI. All links on an authorized file are
visible in its list result; use a host projection if target identities need finer access control.

The older reference coordinator is a separate, opt-in retention protocol. It does not
populate these links; existing consumers keep working. Categories and scopes remain
compatible policy metadata and are not inferred from links.

## Retention holds and references

`reserve`, `attach` and `release` take a hold ID and a consumer. An active hold blocks
deletion. Unresolved reservations are kept indefinitely. Released hold IDs are permanent
tombstones and cannot be reused.

`createFileReferenceCoordinator({ storage, references, authorize })` moves each reference
through `intent → bound → detaching → released`. It never compensates for an uncertain
outcome; call `reconcile` with the recorded actor to recover. `references.pending(tenantId,
limit)` returns bounded recovery batches for your worker.

## Audit

Every mutation appends an audit event to the partition outbox in the same transaction.
`createFileAuditDispatcher` appends pending events to the ledger, then acknowledges only
those event IDs. A lost acknowledgment is safe to retry. When 2,000 events are pending,
mutations fail with `PRECONDITION_FAILED` until delivery succeeds. No events are dropped.
Your application schedules the worker; importing the package starts nothing.

## Private files and versioned documents

- `createPrivateFileStore({ bucket, region, prefix })` supports domains that own their
  per-file metadata, such as email attachments. It provides an immutable `put`, 60-second
  attachment downloads and `remove`, which deletes every version and delete marker. It
  does not use the library's quotas or holds. Pair it with `scanPrivateFileBytes` when
  your policy requires malware scanning.
- `createVersionedDocumentStorage` is a compatibility adapter for domains that own their
  object keys. Its verification checks metadata only: version, size and type.

## Errors

Expected failures throw `FileStorageError` with a `code` of `INVALID_INPUT`,
`NOT_FOUND`, `TOO_LARGE`, `FORBIDDEN`, `CONFLICT` or `PRECONDITION_FAILED`. Map these to
your transport. Schema violations throw Zod errors; `formatFileValidationError` turns
them into safe, field-specific messages. Treat other errors as internal and retryable.

## Limits

- Files are limited to 50 MiB. The type is resolved at `begin`. A file whose bytes
  turn out to be another accepted type is quarantined, not retyped.
- Each tenant partition holds at most 500 lifetime file records, including deleted files.
  Each file allows 20 lifetime hold IDs, and each partition allows 2,000 pending audit
  events. These limits reject growth explicitly; they are not production capacity claims.
- Removal is soft. It hides the file and denies downloads, but it does not erase bytes or
  release quota. Diagnostics report cleanup candidates without deleting anything. No
  prune executor exists.
- Provider and scanner calls have a 15-second default deadline, configurable up to 30
  seconds. The ClamAV adapter requires a trusted private TCP endpoint and signatures less
  than 72 hours old.
- Issued S3 presigned URLs cannot be revoked before they expire.

### Linked uploads and browser previews

Pass optional `links: [{ type, targetId }]` to `begin` to bind a new upload to application records from the start. Each target requires `link` authorization against the proposed pending file. Links and the upload intent commit atomically, obey `maxLinksPerType`, and are included in the idempotency input. Retrying with another target fails rather than moving the upload. Links still confer neither access rights nor retention holds.

`canPreviewFile(file)` is a browser-safe eligibility helper for available, byte-recognized PDFs and supported raster images. `preview(actor, fileId)` rechecks download authorization and availability, then requests an inline, version-pinned URL with the same short lifetime as downloads. HTML, SVG, office documents and unrecognized types remain download-only. Preview is browser-native; there are no thumbnails or conversion jobs. The S3 adapter honors inline disposition; custom object drivers must honor the optional `disposition` argument to display previews. Normal downloads remain attachments.
