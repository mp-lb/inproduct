MyShop is a private, local-only React/Vite frontend with a Node HTTP backend.
It demonstrates the public InProduct libraries with a real client/server boundary.
It is not Next.js. There are no real payments, orders or customer records.

## Reproducible setup

Install Node.js 22.13+, pnpm 11 and Zapper, then clone the repository:

```sh
git clone https://github.com/mp-lb/inproduct.git
cd inproduct
zap task setup
zap task context-build
zap task myshop
zap launch MyShop
zap status
```

`zap task myshop` builds the libraries and starts `myshop-backend` and
`myshop-frontend`. Zap allocates both ports; no database credentials or external
services are needed. Only the optional data jobs section needs the local MongoDB service. The separate `landing-page` service runs the public marketing site.

## Storefront and products

Four deterministic products are loaded from `apps/myshop-frontend/src/catalog.ts`:
Everyday mug ($18), Market tote ($24), Field notebook ($12) and Desk plant ($16).
Prices use USD cents.

1. Add a mug and tote to the cart. Adjust quantities or remove an item.
2. Open **Admin → Manage products**, add a product and watch its slug preview update.
3. Rename or reprice a product. The storefront and existing cart lines update together.
4. Try a duplicate name or punctuation-only name to see application validation.
5. Delete a product; it disappears from the storefront and cart.
6. Select **Reset demo** to restore the products and clear the cart.

Product slugs come from `@mp-lb/inproduct`. Catalog/cart logic remains example
frontend code held in the current tab. There is no checkout or order creation.

## File storage through the backend

Open **Admin → File storage**. Upload a file (up to 10 MiB) or choose **Add example
file**. Search names/tags, filter tag, edit metadata, download, or confirm
deletion. Usage totals cover all files regardless of filters; longer lists paginate.

The backend creates a file service with the library's disk adapter and mounts its
HTTP handler. The frontend creates an HTTP client and passes it to the headless hook.
The app supplies navigation, its table and forms; the library supplies file operations,
validation, transport, persistence and async state. See [File storage](/docs/storage).

Files and metadata are saved in ignored `apps/myshop-backend/.data/files`. They survive
browser reloads, frontend/backend restarts and **Reset demo**. Delete files explicitly
in File storage. Files are not malware-scanned; no production storage is accessed.

## Data jobs against a disposable MongoDB

Data jobs need the project's local MongoDB service. Start it with `zap up mongodb`,
then open **Admin → Data jobs**. The jobs use the disposable `myshop_demo` database.
Without MongoDB, the section shows an error, and the rest of MyShop keeps working.

1. Run **Reset demo products**. This app-defined job replaces the collection with
   synthetic legacy products. Archived products still have the retired `legacyPrice` and
   `internal.notes` fields. One active product keeps them on purpose.
2. Inspect **Remove legacy product fields**. It is the built-in job, scoped to archived
   products. The preview shows the count for each field, the scope, the data-loss
   warning and the retry policy.
3. Tick the acknowledgement, and confirm. The panel shows progress, the outcome and verification.
4. Inspect and run it again. Nothing is left to remove, and the second run changes nothing.

The same jobs run from the terminal:

```sh
zap task myshop-data-jobs -- list
zap task myshop-data-jobs -- inspect remove-legacy-product-fields
zap task myshop-data-jobs -- run remove-legacy-product-fields --accept-data-loss
zap task myshop-data-jobs -- verify remove-legacy-product-fields --json
```

The CLI loads only the job definitions and the MongoDB driver, not the MyShop server.
The backend exposes the jobs through a local tRPC router at `/api/trpc`, and the
frontend mounts the library's framework-free panel. See [Data jobs](/docs/data-jobs).

## Local-only boundary

Both MyShop packages are private, excluded from automatic publishing and ordinary builds, and
have no production start script. `zap task myshop-check` builds both explicitly for
local verification. Both services bind to loopback. The backend checks request hosts
and origins, but has no production login or multi-user authorization.

Never expose either service through a tunnel or add it to hosting/deployment settings.
Stop with `zap down myshop-frontend myshop-backend`. Inspect logs with
`zap logs myshop-frontend --no-follow` or `zap logs myshop-backend --no-follow`.
